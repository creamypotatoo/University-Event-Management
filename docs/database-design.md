# Database design and migration review

## Normalization and relationships

The nine tables separate identity, student attributes, clubs, administrator assignments, venues, events, registrations, memberships, and expenses. Each non-key attribute describes its row's entity; names, department, venue details, and expense totals are not copied into associative rows. Totals and attendance counts are derived with joins and aggregation rather than stored. The design follows third normal form for the stated attributes.

A User has zero or one Student profile. Students and Events have a many-to-many relationship through Registration; Students and Clubs have a many-to-many relationship through ClubMembership. ClubAdmin maps users to clubs independently of student membership. A Club and a Venue can each have many Events; every Event has exactly one Club and one Venue. Each EventExpense has exactly one Event. Explicit association objects retain status and timestamps rather than hiding these attributes behind a secondary relationship.

User.role is the coarse system role; ClubAdmin identifies which clubs an administrator manages. Database foreign keys ensure the assigned user exists. Agreement between role and assignments, and permission enforcement, are Phase 3 application rules. A student profile is optional for administrators. User email must be trimmed and lowercase; callers must normalize before insertion. Club and venue names and student numbers are case-sensitive unique identifiers in this version.

## Lifecycle and cancellation

- Registration has one lifetime row per `(event_id, student_id)`, including cancelled rows. Status values: `registered`, `cancelled`, `attended`.
- ClubMembership has one lifetime row per `(club_id, student_id)`. Status values: `active`, `cancelled`.
- Cancellation updates status; reactivation updates the existing row. Retain the original joined_at/registered_at timestamp. This prevents duplicate active rows and retains cancelled records, but does not provide a full history of cancellation cycles. An audit table would be a separate future enhancement.
- Event status values: `scheduled`, `completed`, `cancelled`. Users: `student`, `club_admin`, `system_admin`.
- Foreign keys restrict parent deletion to preserve participation and expense records. No cascading deletion is configured.

## Venue scheduling and capacity

PostgreSQL enforces non-overlapping bookings at the database level using a GiST exclusion constraint combining venue equality with overlapping timezone-aware ranges. The half-open interval `[start, end)` allows adjacent bookings. Cancelled events do not reserve a venue; completed events still preserve their historical booking. Moving, rescheduling, or reactivating an event is also checked. The migration installs `btree_gist` if necessary; PostgreSQL documents it as a trusted extension installable by a database user with CREATE privilege. See [btree_gist](https://www.postgresql.org/docs/current/btree-gist.html) and [range exclusions](https://www.postgresql.org/docs/current/rangetypes.html).

CHECK constraints enforce positive venue/event capacities, end_time > start_time, nonnegative expense amounts, valid statuses, and selected nonblank text. Event expenses use exact NUMERIC(12,2); amounts are assumed to be BDT. PostgreSQL timestamps are timezone-aware; application input should include an offset.

Phase 5 implements the cross-row rules in transactional services: event capacity cannot exceed venue capacity, occupied registrations cannot exceed event capacity, and closed events reject registration. These rules are not simple row CHECKs. Services lock the Event row with SELECT FOR UPDATE, refresh its state, check status and occupied count, and insert/reactivate within the same transaction. Event/venue capacity edits use compatible locks. The schema alone does not guarantee capacity limits for direct SQL writers; see the [Phase 5 locking contract](phase5-events.md).

SQLite intentionally omits the PostgreSQL exclusion constraint. SQLite tests exercise portable constraints with foreign-key enforcement enabled, but cannot verify venue conflict enforcement or PostgreSQL concurrency.

## Reviewed initial migration

Revision `0001_initial` was autogenerated against the actual local PostgreSQL database using an explicitly read-only transaction. Public schema inspection found zero existing tables. The generator deliberately avoids initializing an Alembic version table during inspection.

Review findings:

- Upgrade adds `btree_gist`, nine domain tables, indexes, named checks, unique constraints, foreign keys, and the venue exclusion constraint. Alembic creates its version table when the upgrade is applied.
- Tables are created in dependency order; all mandatory fields are NOT NULL. Each foreign-key lookup is covered by a standalone index or the leading columns of a unique/composite index.
- PostgreSQL defaults supply creation/participation timestamps and initial statuses.
- Upgrade contains no DROP, DELETE, TRUNCATE, or existing-data updates. PostgreSQL executes the DDL transactionally.
- The generated downgrade contains destructive table-removal operations for migration completeness. It has not been executed and must not be run on a database with data. `btree_gist` is deliberately preserved by downgrade because other objects may depend on it.
- Applying the upgrade and running the seed command require user approval. Neither is invoked automatically.

The user subsequently approved the upgrade and PostgreSQL tests on 2026-11-11. Revision `0001_initial` was applied successfully, `db current` reported head, and `db check` found no new upgrade operations. All 26 PostgreSQL cases passed. Final read-only counts showed zero rows in all domain tables after test rollback. The development seed command was not run. Alembic comparison has limits for detecting some CHECK/exclusion changes; native constraint tests complement it.

## Integration test isolation

Phase 4 adds the approved `clubs.is_active BOOLEAN NOT NULL DEFAULT true` field with revision `0002_club_active`, without altering the existing constraints. See the [management design and migration review](phase4-management.md) for deactivation semantics and the venue-capacity edit guard. Phase 5 uses the same schema for event creation and registration capacity transactions.

`pytest --postgres` explicitly opts into the configured local development database after migration approval and application. Standard tests insert unique fixtures inside an outer transaction; sessions use savepoints and final teardown rolls back the test rows. The separately approved `--postgres-concurrency` tests need committed UUID fixtures visible across connections, then remove only their own fixture IDs. Neither mode drops/resets schemas or runs seed-dev. Sequence counters can advance. Run locally without other writers or parallel pytest workers. See [Phase 5 test safety](phase5-events.md) for independent-connection race coverage and cleanup.
